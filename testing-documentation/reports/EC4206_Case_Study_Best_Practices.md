# EC4206 Section 3.10 - Case Study and Testing Best Practices

## Problem, purpose and architecture

Students need a convenient way to find current campus information such as library hours, event dates, timetables and locations. Administrators need a controlled way to maintain those records so that changes are reflected in the information students receive. The Smart Campus Assistant is a coursework implementation of this shared information service. The tests use synthetic data, and the project records no institutional deployment or user adoption study. [Project documentation](../../README.md)

The React and TypeScript frontend uses Vite and calls a Node.js and Express API. Mongoose connects the API to MongoDB, which stores accounts, sessions and the five campus collections: events, announcements, schedules, library resources and locations. Students can register, sign in, navigate protected campus pages, search records, ask the assistant questions and manage account settings. Administrators can create, edit and delete campus records through the administrator dashboard. The API checks the session and user role for protected writes, while the browser also restricts navigation to administrator pages. The assistant uses deterministic keyword matching and current database records. [Architecture and API](../../README.md) / [Test plan](../test-plans/EC4206_Test_Plan.md)

## Case study: publishing and finding library hours

The representative workflow begins with an administrator changing the opening hours for a campus location. A student should then be able to retrieve the revised hours through the campus information service and obtain the same answer from the assistant. This workflow crosses access control, persistence, the student-facing API and browser presentation. The test plan maps these responsibilities to FR-06, FR-08 and FR-09. [Requirements traceability matrix](../test-plans/EC4206_Test_Plan.md#8-requirements-to-test-traceability-matrix)

Cucumber scenario **BDD-01** verified that an administrator update reached the student-facing locations API and that the assistant returned the same hours with the same MongoDB location identifier. In separate browser fixtures, **AUTO-03** exercised navigation to the campus locations page and **AUTO-05** verified that the assistant displayed the stored synthetic library name and hours. The planned validation exercise, in which a person finds and interprets revised hours without guidance, remains **Not Run**. TC-028 subsequently verified the complete browser workflow with a single synthetic library fixture and separate sessions. Human task completion and interpretation remain for participant evaluation. ## Continuous quality in Agile and DevOps

Acceptance criteria expressed in Cucumber give developers and testers a shared description of expected behaviour. Unit tests and targeted API regressions give feedback on small changes, while Selenium checks that representative workflows still function through the browser. For an Agile iteration, a team can attach the scenario identifier and failing evidence to a defect, implement a focused fix, and confirm it against acceptance criteria and regression checks before closing the item.

GitHub Actions runs repeatable verification on pushes and pull requests. It uses a MongoDB service, installs locked dependencies with lifecycle scripts disabled, and preserves run artifacts for investigation. The SonarQube job follows successful verification for eligible events and uses secretless OIDC. Its Quality Gate is a separate result from workflow success. The initial hosted workflow succeeded while the gate failed at new-code security rating **C**. The follow-up pinned two SonarSource actions to verified full commit SHAs and disabled lifecycle scripts in both dependency installs. SonarQube marked all four findings fixed and passed the remediation commit with new-code security rating **A**. The workflow produced a verified frontend build artifact. Deployment and production acceptance remain outside the recorded workflow. [CI configuration](../../.github/workflows/ec4206-ci.yml) / [Quality Gate history and evidence](EC4206_SonarQube_Quality_Metrics.md#hosted-analysis-after-remediation)

## Limitations

- **Manual and human validation.** TC-001 passed by user confirmation. TC-005 has a partial login observation, and its formal status is Not Run. The other 34 manual cases remain Not Run. Human usability evaluation remains Not Run. Desktop Chrome checks provide interaction evidence for scripted tasks. Accessibility across devices, assistive technology and unaided task completion remain unmeasured.
- **Performance and security scope.** The JMeter result applies to bounded local read traffic at 1, 5, 10 and 20 users with synthetic data. Production capacity, write performance and acceptance against agreed latency and throughput thresholds remain unverified. The eight API security checks cover selected role and validation cases.
- **Coverage and static analysis scope.** Local Node coverage measures 15 backend runtime files. The SonarQube overall project measure covers a broader source scope using backend LCOV. Frontend test coverage remains **Not Measured**, and new-code coverage was uncomputed because the analyzed change had no eligible lines or conditions. The gate passed with **five distinct overall issues still open**, including one security finding, four reliability impacts and two maintainability impacts. Two findings affect both reliability and maintainability. One analysis warning remains, and its text and impact were unavailable in the public evidence. [Section 3.9 report](EC4206_SonarQube_Quality_Metrics.md)

## Recommendations for future testing

1. **Execute the manual catalogue and conduct a human usability session.** Prioritise access control, schedule correction and finding revised library hours. Record actual outcomes for each original case ID. Observe task completion, errors and keyboard navigation with representative participants.
2. **Instrument frontend tests for login recovery and campus search.** Start with same-page recovery after rejected login and the transition from campus search to the assistant. Export frontend LCOV separately, validate its source paths and retain the Selenium workflows as browser regression checks.
3. **Set performance acceptance criteria and retain reproducible evidence.** Agree latency and throughput limits before rerunning the benchmark. Move the corrected launcher into maintained test tooling and require JTL totals, preflight and cleanup transcript, and exit status before accepting a run. Use an isolated staging environment for broader read and write workloads.
4. **Review the five open SonarQube issues and investigate the analysis warning.** Record the warning text from authorised background-task or scanner-log access. Give each open issue an owner, prioritise the security disclosure and reliability findings by impact, add focused regression checks for accepted fixes, and verify closure in a subsequent analysis.
5. **Validate the test harness before starting services.** Add a lightweight module-resolution check for the Selenium entry point and preserve separate assertions for empty and populated event results. These checks address the observed startup and empty-state failures with fast feedback.

## Conclusion

The case study demonstrates how requirement traceability, isolated fixtures and reproducible retests supported a corrected student-facing response, restored browser automation and improved the completeness of benchmark evidence. Hosted CI and the SonarQube gate provide repeatable evidence for the tested revision. The documented gaps in manual execution, human usability, frontend coverage, production-like performance and static analysis remain the basis for future testing.
